This document proposes correcting twelve problems found in the September 10 review of Muskometer. It covers ownership calculations, outstanding-share counts, notification ordering, refresh scheduling, market-close behavior, popover sizing, login settings, and one calendar date. It treats the user's earlier instruction to fix all twelve as authorization to proceed. The work changes the existing application without adding product features or external services.

For ownership, the application would start with a verified, dated baseline and keep separate dated balances for recognized ownership categories. Later Form 4 reports would update only the categories they actually address, preserving unchanged classes, trusts, and options. Transaction dates would determine which observation is newer; submission order and a filing's reporting period would not be sufficient. Amendments would correct historical observations without replacing later balances. A recognized zero would count as a real disposal, while an unknown security would not imply zero.

When incomplete scanning, missing dates, unsupported securities, or conflicting observations prevent a reliable complete answer, synchronization would omit that symbol. The user's previous entire holding would then remain in place. The existing requirement for complete expected-symbol results would stay. Arithmetic and conversions would be checked, stored state would stay bounded, and SEC requests would remain limited and cancellable. The same verified observations must still produce the stated TSLA and SPCX defaults: 710,172,677 and 5,116,475,230 shares respectively.

Outstanding-share facts require a separate correction. The application would retain filing identity when choosing eligible SEC company facts. An original filing and amendment both reporting 100 on the same day must yield 100, rather than a sum of 200. Identical duplicate totals would be acceptable; conflicting totals that cannot be resolved would produce no result. Existing rules for preferred forms, concepts, and valid positive integer totals would remain.

Notification work would separate recording an observation from waiting for delivery. An accepted quote would update chart samples, milestone position, and record state before any notification wait. All enabled thresholds would be evaluated and crossings reserved before delivery begins. Identity and version checks would prevent an older completion from changing newer observations. Failed deliveries would remain retryable while the latest value stays above the threshold. Dropping below it would rearm the threshold, and a subsequent crossing must survive an earlier delivery's completion.

Day-close delivery would distinguish an ongoing attempt from completed or intentionally skipped work. Only confirmed delivery, an already confirmed delivery, or a disabled-feature skip would consume the pending item. Completion would acknowledge the particular day delivered without deleting a newer pending day. Existing saved settings and records would remain readable, and reset or cancellation would invalidate outstanding completions. The design also forbids an unlimited accumulation of refresh-related tasks.

Quote polling would begin immediately using stored or bundled holdings. SEC synchronization would run independently, with at most one owned synchronization task per view model on its existing daily and backoff schedule. Slow SEC responses would therefore not delay quotes. Accepted holding changes could trigger at most one quote recalculation or refetch. Quote completions must use current holdings or be rejected, and stopping or restarting must prevent old work from overwriting new work.

Market-clock advancement would no longer depend on successful quote retrieval. At close, or the first wake afterward, the application would finalize a real session record from its last regular-session sample even if Yahoo fails. It would preserve the observation time and stale status and explain the last-observed basis in notification text. Leaving an observed regular session would trigger one closing quote attempt, with at most one additional bounded retry for a transient failure. Overnight polling and notification retries would remain limited, and scheduling would respect market opens, early closes, holidays, and cancellation. Exact retry timing is not specified.

The main popover would fit available screen height through scrolling while keeping header, footer, and Settings actions reachable. Actual SwiftUI content would be checked at heights of 600, 700, 800, and 900 points. Login settings would distinguish unregistered, enabled, awaiting approval, and unavailable states. Awaiting approval would preserve the preference without repeated registration; explicit disabling would still unregister. Tests would mock this boundary without changing real login items. December 31, 2027 would become a regular trading day, preserving the remaining calendar entries.

Delivery includes reorganizing and retaining all 248 baseline tests, adding failing regressions before fixes, rerunning compatible reproduction probes, full verification, separate live-data checks, popover checks, and independent final review. Main risks are ownership ambiguity, concurrency and retry regressions, lost tests, stale-price labeling, and leaked tasks. Bounded state and the 400-sample cap remain requirements. Deployment, release, exhaustive long-duration memory certification, and claims of real notification or login authorization are excluded. The document lists no deferred work.

## Summary

The proposal repairs all twelve reviewed problems while preserving Muskometer's existing features and saved data. Ownership updates would respect partial filings and effective dates; share totals would avoid double counting; notification and refresh work would resist out-of-order completion. Quotes would start without waiting for SEC synchronization, and day-close records could be finalized honestly from the last observed session price.

The visible changes are a popover that fits shorter screens, login settings that handle pending approval correctly, and the corrected December 31, 2027 trading date. Completion requires regression coverage, full verification, live-data checks, and independent review. It does not include a release or production deployment.
